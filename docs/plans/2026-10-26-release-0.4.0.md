# Quimera 0.4.0: definitive release plan

**Goal:** One release that makes Quimera's promises true in real use: the per-task loop actually runs, verification never reports success without evidence, the installer stays inside the project, the git flow works in brand-new local projects, memory survives and stays current, and the cost profile has an effect.
**Depth:** Risky (the installer writes and deletes files in user repositories; verification decides push readiness).
**Baseline:** `0.3.0`, commit `13106c4`, branch `docs/improvement-plan`.
**Status:** Approved by the user on 2026-10-26 with the recommended answers for D1–D5, implemented the same day (WP0–WP14) and released as 0.4.0. Open after the release: the upgrade of the two real pilot projects, with the owner, and Pilot 3 (`evals/rubric.md`).

**Inputs**

1. The external assessment in `docs/plans/2026-10-26-improvement-plan.md` (findings F01–F18, tasks T001–T014).
2. A re-check of that assessment against `13106c4` in disposable repositories ("Assessment check").
3. Two real projects started with Quimera 0.3.0 on this machine, read without changes: **Otica** (Vite + TypeScript + Three.js landing page with a virtual try-on; one session of about 10.5 hours, 1,713 tool calls, 37 commits) and **Rabisco** (Godot 4.7 platformer for Android, no `package.json`; one session of about 5 hours, 9 commits). Evidence comes from their repositories, memory files and session transcripts ("Pilot findings").
4. A comparison with current upstream kits ("Positioning").

## Summary

The external assessment is accurate: every finding it reproduced was reproduced again. It looked at the scripts and the text. The pilots show a larger problem it could not see: **after kickoff, the method did not run.** In both projects, `task-start`, `writing-plans`, `verification`, `code-review` and `close-task` were never read. No review ran, the model profile changed nothing (both sessions ran entirely on the strongest model), memory went stale, and no `main` branch was ever created. The scripts' false successes made this invisible: `verify.mjs` reported `ok` with lint and tests skipped, and the preflight reported `ready` in a repository with no commits.

So this release does two things with equal priority:

1. **Make the scripts truthful and safe** (the assessment's Phase 1, plus the pilot's git findings).
2. **Make the method activate and fit the person using it** (new, from the pilots): an always-loaded working loop, memory that is checked for staleness, reviews triggered by phases rather than pushes, tiers that actually route work, and a kickoff that learns who the owner is and what kind of product it is.

The assessment's four-release roadmap (0.3.1 → 1.0.0) becomes one release, `0.4.0`, built from focused branches, because the kit has no outside users yet (public repository, no releases, no issues) and the user asked for a single update.

## How the pilots are used for testing

Otica and Rabisco are evidence and acceptance targets, not test fixtures: they hold private product code and art, and the kit's tests must run on any machine.

1. **Synthetic fixtures copy their shape, not their content.** `tests/fixtures/` builds, at test time, small repositories that reproduce what the pilots taught: a single-package Vite/TypeScript project with `typecheck` and `build` scripts and no `test`; a Godot-like project without `package.json` that declares its own check; local-only + discreet profiles; an unborn repository; a chain of stacked task branches; a stale `STATE.md`; 0.3.0 manifests with `source: null` and with a commit.
2. **Migration test on copies.** Before release, each pilot is copied into the scratch area (a local `git clone` plus its untracked Quimera and memory files); `update` 0.3.0 → 0.4.0, `doctor` and `verify` run there. Tests never touch the originals.
3. **Transcripts seed the evaluation scenarios** (WP14), rewritten in our own words, with no product secrets or personal data.
4. **Pilot 3 measures the result.** After release, the next real session (a new small project, or the next phase of Otica or Rabisco) records: loop steps executed per task, `STATE.md` freshness, owner rejections of "done" claims, share of turns per tier, and cost. These numbers, compared with the two sessions above, are the evidence for any claim in the README.
5. **Real upgrade last, with consent.** After the release gate, offer to update both real projects and to repair their branch layout and memory (create `main`, integrate finished work, refresh `STATE.md`, `MAP.md`, `AGENTS.md`), one confirmation per step.

## Positioning

Checked on 2026-10-26 from primary sources (READMEs, release notes, docs): Superpowers v7.0.1, Spec Kit v1.2.3, BMAD-METHOD v6.12.4 (stable line), Agent OS v3.0.0, and three kits that grew in 2025–2026: OpenSpec v1.15.0, Compound Engineering v3.32.2 and GSD Core v1.18.0. This is a bounded comparison of documented capabilities, not a benchmark.

**Not unique to Quimera** (exists elsewhere): proportional depths (GSD, Compound Engineering, Superpowers, BMAD); memory files (GSD `STATE.md`, BMAD project context); hash-based safe updates (Spec Kit, GSD); local-only options (GSD, BMAD); model profiles (GSD `quality`/`balanced`/`budget`); specialist reviewers (Compound Engineering personas, BMAD lenses); a study round with an independent judge (Compound Engineering bake-off); chat language separate from file language (BMAD v6).

**Probably unique** (not found in any of the seven): a commit-msg guard shipped in the kit that strips AI attribution whatever tool wrote it; a per-project git identity check every session; a changed-files verification script (uncertain for two kits, and JavaScript/TypeScript only today); model tables for two-size providers with the rule that the small model never reviews its own code.

**Where Quimera is behind:** no tests or CI for the kit itself (every other kit except Agent OS has them); no releases or pinning (Spec Kit `--tag`, BMAD `--pin`, OpenSpec checksummed binaries, GSD on npm); 5 named tools against 14–46 elsewhere; verification limited to JavaScript/TypeScript and never a gate; no context-size guard for skills (Superpowers fails a test above 20 KB per skill); no real cross-model review dispatch (Compound Engineering, GSD call other vendors' command-line tools).

**Positioning for 0.4.0:** *a small, local-first standard for one owner working with several AI tools: decisions live in the repository, the git history stays the owner's, and nothing counts as done without evidence.* The differentiators to claim are the combination, each only once demonstrated:

1. **The owner stays in control of the history:** discreet mode, identity per project and machine, a branch flow that ends integrated on `main` even without a remote (WP7, WP8).
2. **Honest evidence:** verification states passed, failed, unverified or not applicable, for any stack that declares its checks (WP5).
3. **Fits a non-technical owner:** the profile decides how technical the conversation is, and what is learned about the owner stays in the project (WP10). The Portuguese-speaking owner is served first.
4. **Proportional cost, measured:** tiers that actually route work, with Pilot 3 numbers before any savings claim (WP11).
5. **Small and inspectable:** Markdown and a few dependency-free scripts, no telemetry (OpenSpec, for comparison, enables telemetry by default), nothing runs on its own.

README claims to replace (WP13): "adds what none of them covers" (only true for the items under "Probably unique"); "works with any tool" (say: five named tools, any other through the generic adapter); "model profiles for any provider" (say: five providers); "never overwrites a file it did not create" (true only after WP2).

Gaps accepted for now: native plugin and marketplace packaging, cross-model review dispatch, and autonomous pipelines that watch pull requests (the last conflicts with kit rule 6).

## Global constraints

The assessment's "Global constraints" apply unchanged: files in English except `README.pt-BR.md`; skills name actions, not tools; frontmatter only `name` and `description`; every skill ends with Provenance; never the BMAD trademark names; nothing installs dependencies, starts servers, calls the network or runs code by itself except the opt-in commit-msg guard (see D5); the kit's own CI runs only when dispatched by hand; never overwrite unknown files, follow outside-root paths or delete edited files; push only with the user's agreement each time; installer changes are tested in a scratch repository (`init` → edit → `update` → `doctor`) before commit.

## Work packages

Each package is one focused branch (or a short series of commits) with its regression tests, merged into `main` locally after its gate. Nothing is pushed until WP15, and then only with the user's agreement. File lists are the expected set.

### Part A · Truthful and safe scripts

#### WP0 · Test harness (T001)

- **Files:** `tests/helpers/repository.mjs`, `tests/fixtures/*.mjs`, `package.json` (`"test": "node --test tests/"`, `"check": "node dev/check-content.mjs"`; no lifecycle scripts).
- **Contract:** every fixture gets a fresh temporary root, `HOME` inside it, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, a fixture identity and no remote. Command results expose status, stdout and stderr. Node built-ins only.
- **Gate:** `npm test` green with positive controls (valid `init`, edit preserved on `update`, dry-run writes nothing). Each later package adds its failing regression first.
- **Commit:** `test: add isolated repository contract fixtures`.

#### WP1 · Valid skills and content checks (F01, part of F10/F15/F18)

- **Files:** the three F01 skills; every skill's `description` (quoted for consistency); `dev/check-content.mjs`; `tests/content.test.mjs`; wording in `close-task` and `code-standards`.
- **Rules checked:** frontmatter is exactly `name` + `description`; `name` equals the folder; `description` parses with `JSON.parse`; `## Provenance` ends the file; every referenced `references/` or `templates/` file exists; no BMAD trademark names; no gendered pronouns for the user; each `SKILL.md` under a size budget (advisory above 12 KB, failure above 20 KB) so always-loaded context stays small. Format failures fail; style notes are advisory.
- **Gate:** the three original files fail; 15/15 pass; a malformed fixture is rejected; PyYAML cross-check when available.
- **Commit:** `fix: make skill metadata valid and verifiable`.

#### WP2 · Contained installer (F02, F03)

- **Files:** `bin/quimera.mjs`, `bin/lib/paths.mjs`, `tests/installer-safety.test.mjs`.
- **Contract:** before any write or delete, validate the whole manifest: known schema, 64-hex digests, relative POSIX paths, no `..`, no absolute paths, no `.git` segment, no duplicates after normalization, every destination inside an allowed root (`.quimera/`, `.agents/skills/`, `.claude/skills/`, `.claude/agents/`, `.github/skills/`, `.cursor/skills/`, `CLAUDE.md`, `.github/copilot-instructions.md`). Resolve each parent with `realpath` and refuse symlinked parents. Invalid input aborts with no change.
- **Helpers:** `init` and `doctor` run the bundled kit's code by absolute kit path, never the copy inside the project.
- **Gate:** crafted `../`, absolute, `.git/hooks/x`, symlinked parent, malformed digest and replaced helper are rejected; an outside sentinel stays byte-identical; normal `init` and `update` unchanged.
- **Commit:** `fix: contain managed file operations and trust bundled helpers`.

#### WP3 · Truthful CLI (F05, F08)

- **Files:** `bin/quimera.mjs`, `tests/installer.test.mjs`, both READMEs (exit codes).
- **Contract:** per-command allowed flags; values validated before any write (`--mode` in `discreet|open`, `--tools` non-empty and known, `--models` known); unknown command or flag exits 64 with help on stderr; operational failure exits 1 and names the failed step; child exit codes, spawn errors and signals propagate; a partial install lists what was and was not done.
- **Gate:** hook conflict makes `init` exit 1 and list what was written; `--mode=banana`, `--tools=` and `updat` create nothing and exit 64.
- **Commit:** `fix: report setup failures and reject invalid input`.

#### WP4 · Preflight that tells the truth (F13, Q01, Q04)

- **Files:** `scripts/git-preflight.mjs`, `tests/preflight.test.mjs`.
- **Contract:** offline by default; `--fetch` fetches the upstream's remote only when asked. Profile fields validated (mode in `discreet|open`, identity `Name <email>`; `TBD` or malformed values need attention). New checks: unborn `HEAD` or no default branch; current branch carries commits of another unmerged task branch (stacked); uncommitted work older than a threshold; default branch taken from the remote, then `init.defaultBranch`, then existing `main`/`master`, never invented.
- **Memory freshness:** a shared helper (`scripts/lib/memory.mjs`) compares `STATE.md` with the repository: its "Updated" date against the last commit, its branch line against the current branch, commits since it last changed (committed mode) or modification time (local-only), and size over a limit. Stale memory needs attention.
- **Gate:** malformed profile is not ready; a mocked Git runner proves no fetch without `--fetch`; unborn, stacked and stale-memory fixtures report attention.
- **Commit:** `fix: run preflight offline and detect missing branches and stale memory`.

#### WP5 · Evidence-aware verification (F04, F17, Q01, Q03, Q07; T005 + T011)

- **Files:** `scripts/verify.mjs`, `skills/verification/SKILL.md`, `templates/AGENTS.md`, `docs/verification-contract.md`, `tests/verification.test.mjs`.
- **Contract:** each step ends `passed | failed | unverified | not-applicable`; the result is `failed` if any step failed, `unverified` if a required step has no evidence, `passed` only when every required step ran. The final line always carries the counts (`Result: unverified · 1 passed, 2 skipped`), so reading only the last line still tells the truth. `push` with no base or zero executed checks is `unverified` (exit 3). Deletions and config changes anywhere on the branch keep the full plan. `--json` prints the report (scope, base, commands, counts, revision). The memory-freshness helper adds one warning line when `STATE.md` is stale, because `verify.mjs` is the script agents run most.
- **Declared checks:** an optional, user-owned `.quimera/checks.json` lists checks as executable-plus-arguments arrays with a name, a working directory and `when: changed | push`. When present it replaces script detection; when absent and there is no `package.json`, the result is `unverified` with the next step ("declare your checks"), not exit 2. No shell strings, no downloads. Kickoff writes it for non-Node stacks (Rabisco: `["bash", "tools/verify.sh"]`).
- **Skill:** the claim → proof table gains rows for visual work (full-resolution screenshots at the project's widths, including the widest, for the changed section and its neighbours), device targets (on a real device when the product targets one), games and interactive flows (failure paths: unreachable goals, soft-locks, camera; a headless bot when possible), and a match against the approved reference. Owner rejection is recorded as a failed check.
- **Gate:** zero-check fixture is unverified; old deletion runs the failing test and fails; stacked or unborn fixture is unverified with a reason; Godot-like fixture runs its declared command; docs-only change is `not-applicable` with the reason.
- **Commits:** `fix: distinguish verification success from missing evidence`, `feat: support declared project checks`.

#### WP6 · Recoverable updates and a diagnostic doctor (F06, F09, Q05; T006)

- **Files:** `bin/quimera.mjs`, `bin/lib/manifest.mjs`, `tests/update.test.mjs`, `tests/doctor.test.mjs`, `docs/update-recovery.md`.
- **Contract:** manifest schema 2 with `desired` (tools, models, mode, localOnly, specialists), `installed` (digests, kit version, source), `pending` (offers, orphans) and `hook` (path, digest). 0.3.0 manifests migrate without losing digests (fixtures copy the shape of both pilot manifests, including `source: null`); keys that 0.3.0 wrote with backslashes on Windows are converted to forward slashes after the same path checks (WP2 refuses them until then). The full operation plan is built and validated before the first write; dry-run prints the same plan. A lock file blocks concurrent runs; an interrupted run keeps the old manifest and leaves a recovery note. Role agents for specialists turned off in the profile are not installed (`--specialists`).
- **Doctor:** read-only, two sections. Installation: missing, edited, pending offers, orphans, diverged mirrors, hook state, profile vs manifest drift. Work readiness: the preflight, including memory freshness. Exit 0 only when installation is healthy; readiness is reported separately. `--json`.
- **Update:** `--tools` changes the tool set explicitly (adds mirrors, removes untouched ones).
- **Gate:** repeated update is idempotent; edit preserved; offer detected after a clean commit; removed upstream file; simulated interruption; malformed manifest; concurrent run; tool change round trip; both pilot copies migrate and `doctor` reports them correctly.
- **Commit:** `feat: track update state and diagnose installations`.

#### WP7 · Local-only that keeps ownership and memory (F07, Q02; T007)

- **Files:** `scripts/local-only.mjs`, `scripts/install-hooks.mjs`, `scripts/commit-msg`, `skills/project-kickoff/SKILL.md`, `tests/local-only.test.mjs`, `tests/hooks.test.mjs`.
- **Exclusions:** exact managed files from the manifest plus the memory files kickoff registers; product documents (`docs/vision/`, studies, plans, reviews) are excluded only if the owner chooses so at kickoff. Already tracked files are listed, never untracked.
- **Kickoff recommendation fixed:** discreet mode no longer implies local-only. Local-only is recommended only for employer or client repositories; the owner's own projects commit memory (discreet still strips AI marks from commits).
- **Memory durability (D1):** in local-only mode, kickoff offers a private Git repository for the memory files inside the project folder (excluded from the project), so they get history and, if the owner chooses, a private remote. The kit never creates a remote or pushes. `doctor` warns when local-only memory has no history.
- **Hook:** temporary file from `mktemp`, errors propagate, the original message is kept if filtering fails; hook digest recorded; updates replace only an unchanged owned hook; custom `core.hooksPath`, worktrees, CRLF and human co-authors covered.
- **Gate:** unrelated untracked standards and skills stay visible; repeated application is idempotent; hook fixtures preserve valid messages.
- **Commits:** `fix: preserve project files and managed hook state`, `feat: keep local-only memory under version control`.

#### WP8 · A branch flow that works without a remote (Q01)

- **Files:** `skills/project-kickoff/SKILL.md`, `skills/task-start/SKILL.md`, `skills/close-task/SKILL.md`, `QUIMERA.md` ("Git").
- **Kickoff:** on an unborn repository, with the owner's ok, create the default branch with a first commit (`chore: start project`, holding `.gitignore` and, in committed mode, the memory files).
- **Task start:** branch from the default branch; never from another task branch unless the owner asks for stacking; if the default branch is missing, fix that first.
- **Close task:** new "Integrate locally" step for projects without a remote or pull requests: after verification and with the owner's ok, `git switch <default>` and `git merge --ff-only <branch>` (or `--no-ff` if preferred), then `git branch -d <branch>`. Never on a dirty tree, never forced. Commit at least at the end of every task, not only at the end of a phase.
- **Gate:** walkthrough in a fresh fixture: kickoff → two tasks → both integrated → `main` holds both, no stacked branches, preflight clean.
- **Commit:** `feat: establish and integrate into the default branch in local projects`.

### Part B · A method that activates and fits the owner

#### WP9 · The loop that runs (Q04, Q08, Q11)

The mechanism is the one file every tool always loads: `AGENTS.md`. Skills load only when triggered, and in long sessions nothing triggered them.

- **Files:** `templates/AGENTS.md`, `templates/CLAUDE.md`, `templates/copilot-instructions.md`, `QUIMERA.md`, descriptions of `task-start`, `close-task`, `code-review`; `skills/close-task/SKILL.md`; `templates/docs/STATE.md`.
- **Working loop in `AGENTS.md`** (at most ten lines, written by kickoff): for every request that changes files, (1) state depth and branch, (2) change, (3) verify with evidence and read the whole result, (4) commit and refresh `STATE.md`; after context compaction or a new session, re-read `AGENTS.md`, `STATE.md` and `MAP.md` before acting; at the end of each phase or milestone, run `code-review` and `close-task` in full.
- **Triggers:** `task-start` is described as "before any change the owner asks for", not "at the start of every task"; `code-review` runs at the end of each phase or milestone and before any delivery to the owner, not only before a push (local projects never push).
- **Memory upkeep:** `STATE.md` has a size limit (about 60 lines) and is rewritten whole, never patched; `AGENTS.md` and `MAP.md` are corrected in the same commit as the change that made them wrong; freshness is checked by `verify.mjs`, preflight and `doctor` (WP4).
- **Failure budget:** an owner rejection of a delivery counts as a failed attempt; after the second, rethink with `systematic-debugging` (or `study-round` for a design or approach problem) before the third delivery.
- **Costly actions:** builds for devices, large downloads and long renders wait until the owner approved what they will show; servers and watchers started for a check are stopped at the end of that check, not only in `close-task`.
- **Gate:** the scenario table in `docs/workflow-contract.md` (WP11) has rows for a long session with ten requests, compaction mid-task, and three owner rejections, each with one unambiguous next action.
- **Commit:** `feat: make the working loop always loaded and checkable`.
